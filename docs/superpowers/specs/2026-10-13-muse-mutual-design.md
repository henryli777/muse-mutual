# MUSE 互助会：首版网站设计

日期：2026-10-13。阶段：设计和实施计划已获确认；产品已上线，独立审查问题已修复。36 项行为测试、类型检查、生产构建与 Node 22/24 CI 通过，匿名访问已验证。

## 目的与范围

创建对外公开的 MUSE 邀请码互助网站，让访客分享邀请码、查看最新分享、复制领取并反馈失效或错误。项目放在 `x_github/muse-mutual` 独立目录；拟建同名公开 GitHub 仓库，网站名称采用用户最后明确的「MUSE 互助会」。

用户明确要求：录入邀请码和剩余次数；剩余默认 30；自动记录并展示最新录入时间；复制使用后扣减一次；提供失效和错误标记。

首版设计假设：公开浏览和分享，无需注册；次数范围 0–30；提交者通过保存在本设备的私密管理凭据修改自己提交的记录。MUSE 邀请码格式和官方总额度尚未提供，因此不凭空限制为某种字符格式，也不把 30 写成经过官方验证的规则。若实际额度不同，可调整上限。

## 页面与视觉

采用暖白背景、深绿色主按钮、圆角卡片和清晰数字，呈现轻量的社区互助板。页面适配手机和桌面，状态同时使用图标、文字和颜色。

首页顺序：

1. 导航：MUSE 互助会、邀请码广场、分享邀请码、使用说明、支持项目。
2. 简短标题：「分享一次机会，让更多人遇见 MUSE。」旁边说明「公开分享 · 免费领取」。
3. 分享表单：邀请码（必填）、预计剩余次数（整数，默认 30）、昵称（选填），提交按钮「分享邀请码」。提交时间由服务端自动生成，无需填写。
4. 邀请码广场：默认最新提交优先；可切换剩余最多，筛选可领取、待核实、已用完。桌面卡片网格，手机单列。
5. 使用说明：分享 → 复制 → 到 MUSE 使用 → 有问题则反馈。
6. 页脚：社区分享说明、项目源码、支持项目。

每张卡片展示：昵称或「匿名分享者」、邀请码、提交时间（完整日期与时间）、预计剩余次数徽标、本站领取次数、复制领取按钮、反馈问题入口。提交者更新余量时另显示更新时间；复制和反馈不改写原提交时间，不用于刷到列表顶部。

所有公开页面和视图（含独立错误页）的「支持项目」链接均使用 `https://support.coinexo.top/`，在滚动时保持桌面与移动导航入口可访问，并在合适位置提供头尾入口。复用共享收款页，不生成新的支付二维码；管理界面和 API 不加入捐款 UI。

新网站使用真实空状态：「还没有邀请码，成为第一位分享者。」不填充看似真实的示例邀请码或虚构社区人数。

## 次数与复制规则

页面文案采用「预计剩余 N 次」，说明：「按分享者填写的余量和本站复制领取记录估算，实际可用次数以 MUSE 为准。」网站无法观察 MUSE 的真实兑换结果，不能把复制次数称为成功兑换次数。

录入时填写当前剩余量，默认 30。如果填 12，发布后展示预计剩余 12，不推断此前成功使用了 18 次。

复制流程：服务端检查记录可领取并短暂预留一个名额 → 浏览器完成剪贴板写入 → 服务端确认领取并扣减一次 → 返回最新次数。剪贴板失败则释放名额；超时未确认的预留自动到期。预留期间名额暂不可被其他请求领取。界面在服务端确认后显示「已复制，预计剩余 N 次」。

如果剪贴板已成功但确认请求暂时失败，显示「已复制，次数同步中」，保留操作 ID 并重试同步；不提示重新领取。每次领取有唯一操作 ID，服务端幂等，重试不重复扣减。对于同一访客、同一邀请码，10 分钟内重复复制仅扣一次，并明确提示已经领取过。窗口过后允许再次领取。

服务端统一保存计数，用数据库条件更新和原子事务保护并发；次数不能为负。任何手动选择文字复制都无法被可靠计量，不假装统计完整。

## 状态规则

| 状态 | 规则 | 表现与操作 |
| --- | --- | --- |
| 可领取 | 剩余 6–30，未被管理员标记失效 | 绿色勾选图标、数字和「可领取」；允许复制 |
| 即将用完 | 剩余 1–5 | 橙色数字和「仅剩 N 次」；允许复制 |
| 已用完 | 剩余 0 | 灰色「已用完」；停止领取，保留原提交时间 |
| 待核实 | 收到问题反馈 | 显示警示图标、反馈数量、原因与「待核实」；仍可领取，优先展示无反馈记录 |
| 已失效 | 管理员核实失效或错误 | 停止领取；从默认可领取列表隐藏，保留状态记录 |

余量状态和投诉状态分别存储，避免投诉覆盖原有计数。管理员核实后可恢复记录；提交者只能更新自己记录的余量，不能自行清除社区反馈。

## 问题反馈与维护

点击「反馈问题」打开小弹窗：选择「已失效」「邀请码错误」「其他问题」，可填简短说明。服务器记录反馈时间。公开界面显示原因类别和数量，不公开原始说明中的潜在个人信息。

同一访客对同一码只计一条有效反馈。单次反馈只标记待核实，不能直接永久下架。首版不把匿名设备识别当成真实身份验证，也不采用未经验证的多次反馈自动定罪规则。

提供受管理凭据保护的维护入口，供运营者查看反馈、标记失效或恢复。管理凭据使用服务端秘密配置，不提交到 GitHub，不向浏览器公开。管理员必须登录维护入口后才能操作。

首版采用服务端提交、复制和反馈限流；邀请码规范化去掉首尾空白后判重，保留原大小写。错误反馈、重复提交、额度耗尽、断网和同步失败都提供具体提示。访客标识使用服务器发放的随机凭据，属于轻量防重复机制，无法完全阻止恶意多设备操作。

## 架构选择

推荐：Sites 托管完整网站，使用 Vinext 服务端和 D1 数据库保存邀请码、领取预留和反馈；另建公开 GitHub 源码仓库供维护和自托管。生产网站需要明确设置为公开访问。

其他选择：自托管 Node + SQLite 可实现同样功能，但需要自行维护服务器；GitHub Pages 静态页面还需外接后端，单独使用浏览器存储无法满足所有访客共享次数，因此不选纯静态实现。

最小数据模型：

- 邀请码：ID、原始邀请码、规范化唯一值、昵称、初始余量、当前余量、确认领取数、创建时间、更新时间、管理凭据哈希、管理员状态。
- 领取：操作 ID、邀请码 ID、访客凭据哈希、状态（预留/确认/取消）、创建及到期时间。
- 反馈：ID、邀请码 ID、访客凭据哈希、原因、私密补充说明、创建时间、审核状态。

所有日期由服务器生成并存储为 UTC，前端按访问者当地时区展示完整日期与时间。列表以创建时间倒序作为「最新分享」排序。

## 验收标准

- 手机和桌面可以公开浏览并提交邀请码；另一个浏览器可以看到同一条记录。
- 默认余量为 30，允许用户填 0–30 整数；错误输入不会创建记录。
- 分享自动生成真实提交时间，列表默认显示最新分享；刷新后数据仍在。
- 复制成功并确认后余量准确扣一；剪贴板失败不扣，确认重试不重复扣，同访客短时重复复制不重复扣。
- 并发领取最后一个名额最多只有一个成功，余量不为负；预留失效后名额可再次领取。
- 余量为零或已核实失效时不能领取。
- 访客可以提交失效或错误反馈，看到待核实标记；单个反馈不直接永久下架。
- 非管理员不能访问审核操作，提交者不能修改他人的邀请码或清除投诉。
- 页面可用键盘操作，状态不依赖颜色；操作结果对辅助技术可读。
- 所有公开页面与错误视图都有正确且滚动时可访问的「支持项目」导航入口，首页头尾保留链接；管理界面无捐款 UI。不展示虚构邀请码、兑换结果或统计。
